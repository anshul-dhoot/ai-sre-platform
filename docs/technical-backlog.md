# Technical & Production Readiness Backlog

This is an inventory for future prioritization, not a delivery commitment or a definition of what the current demo needs. Items marked **Candidate** are unimplemented backlog options. Priorities are relative prompts for discussion: **P1** addresses correctness or reliability when the relevant capability is introduced; **P2** supports operational readiness; **P3** is conditional scaling or infrastructure work. They do not imply a release gate.

## Current implementation and known limitations

| Area | Current implementation | Known limitation |
| --- | --- | --- |
| Application flow | Order Service creates an order in memory and publishes `OrderCreated`; Payment Service consumes it and invokes a simulated processor. | No durable order/payment state or real gateway. The producer does not wait for or handle the Kafka send result. |
| Kafka | Local Compose runs one Kafka 4.1.0 broker/controller, with two topic-default partitions and a persistent local volume. | Single broker and replication factor 1 provide no broker-failure redundancy. A volume helps retain local data across container recreation, not broker/node loss. |
| Consumer | One `payment-service` group member and one listener thread; manual record acknowledgement, auto-commit disabled, earliest reset. | Unhandled invalid/exhausted records stop the listener. Offset/replay behavior has no integration or crash-window coverage. |
| Retry and duplicate handling | Up to three attempts for `RetryablePaymentException`, 250 ms fixed delay; successful order IDs stored in a concurrent in-process set. | No backoff growth/jitter. The set disappears on restart and does not make business effects durable or atomic with offset commits. |
| Event contract and validation | JSON event includes event ID/version/type and payment validation checks required fields and supported version/type. | Contract is duplicated across services; no compatibility policy, payload-size policy, or automated cross-service compatibility check. |
| Tests and operations | Unit tests cover service behavior, event creation and JSON deserialization. | No Kafka integration, restart/crash, broker failure or failure-injection coverage. No runbooks, production alerting, or broader deployment pipeline is present in the inspected repository. |

## Backlog candidates

### Essential correctness and reliability (when the corresponding behavior is introduced)

| ID | Area | Improvement | Problem or risk addressed | Priority | Status | Dependencies / decision triggers | Acceptance criteria |
| --- | --- | --- | --- | --- | --- | --- | --- |
| REL-01 | Producer reliability | Define publication success/failure behavior and handle asynchronous Kafka send results. Consider an outbox only when order state is persisted. | An order can be returned/logged even if event publication later fails; adding separate persistence would create a dual-write gap. | P1 | Candidate | Decide order persistence and caller/API semantics first. See [ADR-002](decisions/ADR-002-kafka-event-transport.md). | Producer failures are surfaced or recoverably recorded; if durable order persistence is added, tests demonstrate no silent loss between state and event publication. |
| REL-02 | Durable idempotency | Coordinate duplicate detection with the durable payment/business operation using a stable event or operation key. | In-memory deduplication only suppresses duplicates within one process lifetime; restart or crash windows can repeat effects. | P1 | Candidate | Trigger when payment effects or state become durable/external. No database is assumed by this item. See [ADR-003](decisions/ADR-003-payment-service-consumer.md). | Replaying the same operation across restart and crash boundaries does not create a second business effect; concurrent duplicate attempts are covered. |
| REL-03 | Offset management | Document and verify commit timing, redelivery and replay semantics under listener failure and process termination. | Acknowledgement timing determines whether work is repeated or skipped around crashes. | P1 | Candidate | Depends on final processing and idempotency semantics. See [ADR-003](decisions/ADR-003-payment-service-consumer.md). | Integration tests demonstrate expected redelivery after failure before acknowledgement and expected progress after successful handling. |
| REL-04 | Retry/backoff | Classify retryable versus permanent failures; define bounded backoff (and jitter if needed) and interruption behavior. | Fixed-delay retries can synchronize load; unbounded or misclassified retries can stall processing or amplify outages. | P1 | Candidate | Revisit when real transient dependencies exist. Current retry policy is specified in ADR-003. | Tests verify only retryable failures retry, attempts remain bounded, permanent failures do not retry, and delay behavior follows the chosen policy. |
| REL-05 | Failed events and replay | Decide whether to retain failed records (for example, a DLQ), alert, inspect and replay safely; define operator procedure. | A poison or repeatedly failing record currently stops the listener and remains uncommitted; no recovery workflow is documented. | P1 | Candidate | Choose based on demo/operational recovery needs; a DLQ and additional topic are not assumed. See [ADR-003](decisions/ADR-003-payment-service-consumer.md). | A permanent and exhausted transient failure has a documented disposition, preserves diagnostic context, and can be safely recovered or deliberately skipped with audit evidence. |
| REL-06 | Event validation | Specify malformed/unknown event handling, payload limits and cross-service contract tests. | Unexpected or oversized messages can fail deserialization or consume resources; current validation is local to Payment Service. | P1 | Candidate | Agree supported payload and compatibility policy. | Tests cover malformed, missing, invalid, oversized and unsupported-version records and verify the chosen handling does not cause uncontrolled repeated failure. |
| REL-07 | Event schema evolution | Define compatibility rules and evolution process for the versioned JSON contract, including unknown event versions. | Producer and consumer changes may otherwise break independently deployed services. | P1 | Candidate | Trigger as multiple event versions or independently deployed consumers are introduced; a schema registry is not presumed. See [ADR-002](decisions/ADR-002-kafka-event-transport.md). | Compatibility expectations are documented and automated checks or contract tests reject a breaking change or prove supported mixed-version behavior. |
| REL-08 | Event ordering | Document entity-key policy and required sequence semantics; test order-sensitive cases. | Kafka ordering is partition-local; changing keys/partitioning can change observed order for one entity. | P2 | Candidate | Define whether order of multiple event types for an order matters. Current `orderId` key decision is in ADR-002. | Policy identifies ordering scope and key; tests verify same-entity ordering for the supported deployment and make no cross-partition ordering claim. |
| REL-09 | Payment workflow | Model payment states, timeout/unknown outcomes and reconciliation before replacing the simulator with a real processor. | A timeout can leave the external outcome ambiguous; retrying blindly may duplicate a charge or leave order/payment state inconsistent. | P1 | Candidate | Trigger only when realistic payment processing is planned; no gateway or persistence required for the demo. | State transitions and timeout/reconciliation behavior are documented and tested, including an ambiguous outcome without duplicate business effect. |

## Prioritization notes

- Correctness items become relevant when the demo adds durable state, external side effects, multiple event versions or operational recovery requirements.
- Operational candidates depend on a target environment and its owners; they do not all need to be completed for a local demonstration.
- Scaling and infrastructure candidates require a demonstrated need. In particular, broker count, partition count, replicas, resources and failure objectives must be chosen together.
- Existing architecture and transport decisions remain in the ADRs; this backlog records follow-up work and links to those decisions rather than restating them as new decisions.
